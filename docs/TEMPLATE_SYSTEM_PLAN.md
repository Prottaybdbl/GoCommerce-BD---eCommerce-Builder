# Template System — Architecture Report

**Project:** Go Commerce BD
**Date:** 2026-10-05
**Scope:** How to build, add, manage, customise, gate and demo 40–50 landing-page templates (Packages 1 & 2) and 20–30 e-commerce templates (Packages 3 & 4)
**Status:** Design proposal. No code has been changed. Read alongside `GoCommerceBD_Master_Plan_v2.md` §5.5 / §5.8 / §11 and `docs/AUDIT_2026-10-04.md`.
**Audience:** You (product owner) + whoever implements this

---

## 0. Executive summary

### 0.1 The one idea that makes this work

> **Templates are DATA. Sections are CODE.**

You do not build 50 landing pages. You build **one section library** (~40 reusable, independently-styled blocks) and then **50 JSON files** that say *which blocks, in what order, with what default content, in what variant, inside what page shell*.

- Adding template #51 = writing a ~150-line JSON file + one screenshot. **No code, no deploy, no review of TypeScript.** 30–60 minutes.
- Adding a design element nobody has built before = adding **one** section type (code, once, ~2–4 hours) — after which every future template can reuse it for free.

That asymmetry is the whole architecture. Everything below exists to protect it.

### 0.2 How your four packages share two libraries

| | Library | Pages | Mechanism |
|---|---|---|---|
| **Package 1** — single landing | `tier: landing` (40–50) | **1** | `limit(store,'pages') = 1`, one layout variant |
| **Package 2** — multi landing | **same** 40–50 | up to 10 | Same manifests, many **page instances** + named **layout variants** for A/B |
| **Package 3** — e-commerce | `tier: shop` (20–30) | home + product + collection | Same manifests, premium sections resolve to `hide`/`downgrade` |
| **Package 4** — e-commerce pro | **same** 20–30 | + more page kinds | Same manifests, premium sections **unlock** |

**Packages 1 and 2 differ by page count and variants, not by template.** **Packages 3 and 4 differ by features, not by design.** Neither pair ever forks a manifest. A template declares `pages` (plural) and its sections declare `requiresFeature`; the resolver does the rest.

### 0.3 Your "template 5 has 3 banners" requirement

Solved by **derived settings forms**. Each section type owns a Zod schema + UI hints. The dashboard does **not** contain a form for "template 5" — it contains a ~15-case `<Field>` renderer that walks the *resolved page tree* and emits controls from schemas.

Template 5's home contains `banner_carousel` with 3 slide instances and `constraints: { slides: { min: 3, max: 3 } }` → the merchant sees **exactly 3 banner upload slots**, no add/remove buttons. A template with no `banner_carousel` renders **zero** banner fields. A template with a 1–6 slide carousel shows the current count plus "Add banner" until 6.

This is automatic and permanent. You never touch dashboard code when you add template #51.

### 0.4 Your demo gallery requirement

Three tiers, in cost order:

1. **Gallery grid** — static WebP screenshots generated by Playwright in CI, pushed to R2, served from `cdn.` with a 1-year immutable cache. 75 templates × ~25 KB = **~1.9 MB total, zero VPS cost, zero DB queries.** Presets are shown as CSS colour-swatch dots, not 450 screenshots.
2. **Live demo** — **one** shared demo store on a **separate hostname**: `demo.yourbrandshop.com/t/{templateId}?preset={presetId}`. Edge-cached for a year with `Cache-Tag`, purged only on template version bump, pre-warmed by a CI crawler. After warm-up the 2 vCPU box serves **~0 requests**.
3. **Merchant preview** — the existing signed-token iframe (Master Plan §5.5), for the merchant's own draft only.

The hard safety rule: **cache key includes only `preset`, validated against the known list, 404 on anything else.** Without that rule, `?utm_source=…` multiplies your cache entries without bound.

### 0.5 Three things that must be fixed before this ships

| ID | Blocker | Why it blocks the template system |
|---|---|---|
| **T-1** | Plan features are **flat, not cumulative** (`packages/db/src/entitlements.ts`) — `package_4` has `shop_pro` but **not** `shop`; `package_2/3/4` never carry `landing` | `requiresFeature: ["shop"]` would hide the section from your most expensive plan. Feature gating is broken on day one. |
| **T-2** | No generic `media` table; `product_images` has a single `url` column and is product-scoped | Banners and logos aren't products. Settings would have to store raw URLs → no `srcset`, no garbage collection, and a return of the `blob:` bug class. Ties to audit **H-11**, **H-10**, **M-18**. |
| **T-3** | `PUT /theme` accepts arbitrary JSON, gated on `products:manage` (audit **H-14**, **M-19**, **M-20**) | A schema-driven editor whose save endpoint validates nothing is not schema-driven. Also a stored-XSS vector via rich text. |

And the standing one: the 4 Oct audit's verdict is **"the project is not clear to go live"** (C1–C8: committed super-admin credentials, second session issuer in production, default secrets, no RLS, no oversell protection, Turnstile bypass literals, no rate limiting). The Master Plan's own rule is "no new features until Phases 0–2 are complete." **Template *authoring* is content work and can run in parallel today. Shipping the template *engine* belongs behind the security gate.** §12 sequences this honestly.

## 1. Where you are today

I read the full theme stack. Here is the actual state, file by file, measured against "50 landing + 25 shop templates, merchant-editable, with template-aware settings forms."

### 1.1 `packages/themes/src/types.ts` — the central constraint

```ts
export type SectionType =
  | "announcement_bar" | "header" | "hero_product" | "video_showcase"
  | "features_list" | "specs_table" | "origin_badge" | "trust_badges"
  | "inline_checkout" | "sticky_bottom_bar" | "faq_accordion";   // 11 total

export interface SectionInstance {
  id: string; type: SectionType; enabled: boolean;
  settings: Record<string, any>;        // ← untyped, unvalidated, unschema'd
}

export interface ThemeTemplate {
  id: string; archetype: ThemeArchetype; name: string; banglaName: string;
  description: string; defaultPreset: string;
  sections: SectionInstance[];          // ← ONE flat page. No `pages`.
}
```

Three fatal gaps for your requirement:

1. **No `version`.** Editing a template silently changes every live store using it.
2. **No `pages`.** `sections` is a single flat array, so a template *is* one page. Package 2 (many pages) and Packages 3/4 (home + product + collection) are inexpressible.
3. **No `tier`, no `requiresFeature`, no per-instance `constraints`.** Nothing distinguishes a landing template from a shop one, nothing gates a premium section, and nothing can express "exactly 3 banners."

`settings: Record<string, any>` is the direct cause of your banner problem: **there is no machine-readable description of what a section accepts**, so no form can be derived from it.

### 1.2 `packages/themes/src/templates.ts` — templates are code, keyed by a 5-value enum

```ts
export const STARTER_TEMPLATES: Record<ThemeArchetype, ThemeTemplate> = { … }
```

429 lines of hardcoded TypeScript objects with inline Bangla copy. Keyed by `ThemeArchetype`, which has exactly 5 values, so **the type system currently permits a maximum of 5 templates.** Template #6 is a compile error. Every new template is a code change, a PR, a build and a deploy.

```ts
}
if (sec.type === "features_list" && store.themeConfig.bulletPoints)  { … }

if (sec.type === "specs_table"    && store.themeConfig.warrantyPeriod) { … }
```

`resolveTheme()` knows the *names of individual settings fields of individual section types*. This is O(section types × fields) hand-written glue. At 40 section types it is unmaintainable; at 55 it is a bug farm. **All of it gets deleted** in the new design — the resolver becomes type-agnostic.

`generateThemeCssVariables(preset)` (emitting `--gocom-primary` … `--gocom-font`) is **good and stays**.

### 1.4 `packages/themes/src/presets.ts` — the one piece in good shape

6 presets (`rose-bold` #E11D48, `emerald-organic` #059669, `midnight-tech` #2563EB, `royal-fashion` #7C3AED, `amber-warm` #D97706, `ocean-clean` #0284C7), each a complete token set. This is your **cheapest variety multiplier**: 75 templates × 6 presets = 450 visually distinct results for zero additional authoring. Keep this file exactly as it is and grow it to 8–10.

One gap: every preset uses `'Hind Siliguri', sans-serif`. Two or three font pairings would multiply variety again at near-zero cost (see §6.4).

### 1.5 `apps/storefront/src/components/SectionDispatcher.astro` — a hardcoded if-chain

Imports 10 section components, then 11 blocks of `{section.type === "…" && <Component … />}`. **Adding a section type means editing this file.** It must become a registry lookup (§3.3).

### 1.6 `apps/storefront/src/components/DynamicThemePage.astro` — one shell for every template

```astro
<main class="max-w-3xl mx-auto px-4 py-6 sm:py-8 space-y-6 sm:space-y-8">
```

Every template, present and future, renders inside the same centred single-column `max-w-3xl` container with uniform vertical rhythm. This is a **hard ceiling on visual variety** — your 50 templates would be 50 reorderings of the same narrow column, and merchants would notice. The page shell must become template-declared (§4.4).

### 1.7 `packages/contracts/src/theme.ts` — the per-archetype-schema anti-pattern

```ts

  "viral-funnel","multi-campaign","fashion-store","tech-gadget","organic-food"
```

Four separate schemas, one per archetype, each enumerating named fields. At 75 templates this becomes 75 schemas. **Schemas must attach to *section types* (~40, reusable), never to templates (75, unique).** That single inversion is what makes derived forms possible.

**This file cannot satisfy your banner requirement and cannot be made to.** "Template 5 has 3 banners, show 3 uploads" requires the form to be *generated*, not written. This view gets replaced wholesale (§5).

### 1.9 Database — `packages/db/src/schema.ts`

Tables present: `user`, `session`, `account`, `verification`, `organization`, `member`, `invitation`, `audit_logs`, `plans`, `subscriptions`, plus stores/products/orders/etc.

**Absent:** `store_themes`, `pages`, `media`, `delivery_zones` (audit **M-18**).

Theme state lives entirely in two columns on `stores`:

```ts
themeArchetype: varchar("theme_archetype", { length: 50 }).default("viral-funnel"),
themeConfig:    jsonb("theme_config").default({}),
```

So there is **no draft/published split, no version, no revision history, no rollback** — contradicting Master Plan §5.5, which specifies `draft`/`published` with one-click rollback.

`product_images` is `{ id, storeId, productId, url, altText, sortOrder, isPrimary, createdAt }` — a **single `url`**, **product-scoped**, with no `widths`, `bytes`, `content_type` or `status`. There is nowhere to put a banner or a logo, and nothing to build a `srcset` from. (See **T-2**.)

### 1.10 `apps/api/src/routes/admin.ts` — `PUT /theme` persists whatever arrives

```ts
themeArchetype: body.themeArchetype || store.themeArchetype,
themeConfig:    body.themeConfig    || store.themeConfig,
```

No Zod parse, no section validation, no sanitisation. Gated on `products:manage` because `theme:manage` does not exist (**H-14**, **M-19**, **M-20**). It does correctly call `purgeStoreCache(store.id, ["theme","home"])` for invariant #8 — but audit **H-5** reports the purge is dead code that reports success anyway.

### 1.11 Entitlements — the flat-features defect (**T-1**)

```ts
package_1: features: ["landing","guest_cod","incomplete_orders","pixel","courier:steadfast"]
package_2: features: ["multi_landing","guest_cod","incomplete_orders","pixel","courier:steadfast","custom_domain","coupons"]
package_3: features: ["shop","customer_accounts","custom_domain","courier:steadfast","courier:pathao","coupons","fraud_rules"]
package_4: features: ["shop_pro","customer_accounts","custom_domain","all_couriers","coupons","advanced_reports","meta_capi"]
```

Read these as sets, not as tiers:

- `package_2` does **not** have `landing`.
- `package_3` does **not** have `landing` or `multi_landing`.
- `package_4` does **not** have `shop`, `landing`, `multi_landing`, `incomplete_orders` or `pixel`.

Consequences today: your most expensive plan loses abandoned-cart recovery and pixel tracking, both of which Package 1 has. Consequences for the template system: a section marked `requiresFeature: ["shop"]` would be **hidden on Package 4**, and any `requiresFeature: ["landing"]` section would be hidden on Packages 2–4. Feature gating would fail on the day it shipped.

There is also no template-related feature or limit of any kind yet. §9.3 gives the fix.

## 2. Architecture overview

```
┌──────────────────────────────────────────────────────────────────────┐
│  CODE LAYER — written once, by developers                            │
│                                                                      │
│  packages/themes/sections/<type>/                                    │
│    Section.astro     render (SSR, zero JS unless needed)             │
│    schema.ts         Zod schema + UI hints  ← drives the form        │
│    meta.ts           name, bn name, category, tier, requiresFeature  │
│    island.tsx        optional Preact island (client:visible)         │
│    variants.css      data-variant style switches                     │
│    fixtures.ts       demo content for gallery screenshots            │
│                                                                      │
│  ~40 landing + ~15 shop section types = ~55, each with 2–4 variants  │
└──────────────────────────────────────────────────────────────────────┘
                                   ▲ referenced by type + variant
┌──────────────────────────────────────────────────────────────────────┐
│  DATA LAYER — written per template, by a designer/content author     │
│                                                                      │
│  packages/themes/templates/landing/fashion-boutique-03.json          │
│    { id, version, tier:"landing", archetype, shell, pages:{…},       │
│      defaultPreset, allowedPresets, requiresFeature, gallery }       │
│                                                                      │
│  50 landing + 25 shop = 75 JSON files. Pure content. No code.        │
└──────────────────────────────────────────────────────────────────────┘
                                   ▲ chosen by merchant, snapshotted
┌──────────────────────────────────────────────────────────────────────┐
│  STORE LAYER — per merchant, in PostgreSQL                           │
│                                                                      │
│  store_themes  templateId, templateVersion, presetId,                │
│                tokenOverrides, globalSections, draft, published      │
│  pages         slug, kind, variantKey, draftSections,                │
│                publishedSections, status, seo                        │
│  media         kind, r2Key, widths[], bytes, contentType, status     │
│                                                                      │
│  `published` is a RESOLVED SNAPSHOT, not a pointer.                  │
│  Editing a manifest can never break a live store.                    │
└──────────────────────────────────────────────────────────────────────┘
```

Four rules hold the design together:

1. **A section type is added once and reused forever.** Templates never contain markup.
2. **A template manifest is data.** It can be authored, reviewed and shipped without a TypeScript build.
3. **The settings form is derived, never written.** Schemas are the single source of truth for the editor, the API validator and the renderer's defaults.
4. **The published store theme is a snapshot.** Template evolution is opt-in per store, with a diff.

### 3.1 Section catalogue

**Chrome (3)** — `announcement_bar`, `header`, `sticky_bottom_bar`

**Hero (5)** — `hero_product`, `hero_split`, `hero_video`, `hero_carousel`, `hero_countdown`

**Social proof (6)** — `trust_badges`, `review_carousel`, `review_grid`, `ugc_gallery`, `logo_strip`, `counter_stats`

**Content (8)** — `features_list`, `features_grid`, `feature_icons`, `specs_table`, `comparison_table`, `rich_text`, `image_text_split`, `benefit_steps`

**Media (3)** — `video_showcase`, `image_gallery`, `before_after`

**Offer (6)** — `offer_banner`, `banner_carousel`, `countdown_timer`, `bundle_offer`, `quantity_discount`, `price_box`

**Conversion (4)** — `inline_checkout`, `order_form_multistep`, `whatsapp_cta`, `call_cta`

**Credibility (6)** — `origin_badge`, `delivery_info`, `return_policy`, `faq_accordion`, `about_seller`, `certification_badges`

**Footer (3)** — `footer_simple`, `footer_links`, `contact_block`

→ **44 landing section types**

**Shop-only (14)** — `product_grid`, `collection_grid`, `category_tiles`, `featured_collection`, `product_card_row`, `search_bar`, `mega_menu`, `breadcrumb`, `filters_sidebar`, `pagination`, `cart_drawer`, `newsletter`, `blog_teaser`, `recently_viewed`

→ **58 total at maturity.** Of these, **11 exist**. Build order in §12.

### 3.2 The combinatorial budget

With 44 landing sections, choosing and ordering 8–12 of them yields combinations in the billions. **50 templates is not a constraint; curation is.** The real work per template is choosing a *coherent* set, writing good Bangla default copy, and picking a variant mix that reads as a deliberate design.

Variety multiplies as:

```
section choice × ordering × variant (2–4 each) × preset (6–10) × shell (5–8)
```

Master Plan §5.5's "variety math" (5 archetypes × 3–4 layout variants ≈ 15–20 templates × 6–8 presets ≈ 100–150 designs) is the same idea at a smaller scale. 75 manifests × 6 presets = **450 distinct storefront looks** from ~58 components.

### 3.3 Registry, not an if-chain

Replace `SectionDispatcher.astro`'s if-chain with a generated registry. One module per section, one index built from the filesystem at build time:

```ts
// packages/themes/src/registry.generated.ts  (generated — do not edit)
import * as announcement_bar from "../sections/announcement_bar/index.js";
import * as banner_carousel  from "../sections/banner_carousel/index.js";
// … one line per section type

export const SECTION_REGISTRY = {
  announcement_bar, banner_carousel, /* … */
} as const;

export type SectionType = keyof typeof SECTION_REGISTRY;   // derived, not hand-listed
```

`SectionType` becomes **derived from the filesystem**, so adding a section folder extends the union automatically — the opposite of today's hand-maintained 11-value union.

The dispatcher collapses to:

```astro
---
import { SECTION_REGISTRY } from "@gocom/themes/registry";
const { section, store, product, ctx } = Astro.props;
const entry = SECTION_REGISTRY[section.type];
if (!entry) return null;              // unknown type → render nothing, never throw
const Component = entry.Component;
---
<Component
  settings={section.settings}
  variant={section.variant ?? entry.meta.defaultVariant}
  store={store} product={product} ctx={ctx}
/>
```

Unknown section types must render nothing rather than throw. A store on an old snapshot referencing a removed section must still load.

### 3.4 Variants: CSS switches over identical DOM

Your words: *"each variant has some similar or new design."* Most "new designs" are the **same content in a different arrangement** — hero image left vs right vs full-bleed; features as a list vs a 2-col grid vs icon cards. That is a variant, not a new section.

**Variants must be `data-variant` attribute switches over identical markup, never divergent markup.**

```astro
---
const { settings, variant = "stacked" } = Astro.props;
---
<section class="gc-hero" data-variant={variant}>
  <div class="gc-hero__media">…</div>
  <div class="gc-hero__body">…</div>
</section>

<style>
  .gc-hero { display: grid; gap: 1rem; }
  .gc-hero[data-variant="stacked"]    { grid-template-columns: 1fr; }
  .gc-hero[data-variant="split-left"] { grid-template-columns: 1fr 1fr; }
  .gc-hero[data-variant="split-right"]{ grid-template-columns: 1fr 1fr; }
  .gc-hero[data-variant="split-right"] .gc-hero__media { order: 2; }
  .gc-hero[data-variant="full-bleed"] .gc-hero__media  { grid-column: 1 / -1; }
  @media (max-width: 640px) {
    .gc-hero[data-variant^="split"] { grid-template-columns: 1fr; }
  }
</style>
```

Why this is non-negotiable: **your CSS budget is 15 KB inlined** (`build.inlineStylesheets: "always"`). Astro inlines the CSS of components actually rendered, so a 10-section page inlines ~10 sections' worth. If each variant were a separate component with its own Tailwind markup, you would ship 2–4× the CSS per section and blow the budget around section #8. As attribute selectors, a variant costs **~100–300 bytes**. 4 variants ≈ 1 KB; 10 sections ≈ 10 KB; inside budget with room to spare.

Operational rules:
- **Budget ≤ 1 KB CSS per section**, all variants included. Enforce in CI (§10.4).
- Variants must be **mobile-identical where it matters.** Bangladesh traffic is ~95% mobile; a `split-left` that doesn't collapse is a bug, not a variant.
- **Mobile-first authoring.** Design the 360 px view, then add desktop via `@media (min-width: …)`.
- Shared primitives (buttons, badges, cards) live in **one** stylesheet consuming `--gocom-*` tokens so they're emitted once, not per section.

### 3.5 Islands: strict JS discipline

JS budget for a landing page is **≤ 30 KB gzipped**. Most sections must ship **zero** JS.

| Pattern | Technique | Cost |
|---|---|---|
| FAQ accordion | `<details>`/`<summary>` | 0 |
| Image carousel | CSS scroll-snap + anchors | 0 |
| Tabs | `:target` or radio+label | 0 |
| Sticky bar | CSS `position: sticky` | 0 |
| Countdown timer | tiny inline script, no framework | ~0.4 KB |
| Checkout form | Preact island, `client:visible` | the bulk of the budget |
| Cart drawer (shop) | Preact island, `client:idle` | shop tier only |

**Only `inline_checkout`, `order_form_multistep` and `cart_drawer` get Preact islands.** Everything else is server-rendered HTML + CSS. A section's `meta.ts` declares `jsBytesEstimate`; CI sums the estimate for a template's default page and fails the build over budget (§10.4).

### 3.6 Section schema + metadata

Each section folder carries its own schema (the form driver), metadata (the gate + catalogue entry) and fixtures (gallery content).

```ts

export const schemaVersion = 1;

export const settingsSchema = z.object({
  slides: z.array(
    z.object({
      image:    imageRef().meta(ui({ control: "image", label: "ব্যানার ছবি",
                                    aspect: "16/9", maxBytes: 300_000, required: true })),

});
```

```ts
  id:       z.string(),                       // stable within the page
  type:     z.string(),                       // must exist in SECTION_REGISTRY

    movable:    z.boolean().default(true),

    variantLocked: z.boolean().default(false),
  }).default({}),

  // Per-instance overrides of schema bounds — THIS is the 3-banner mechanism
  constraints: z.record(z.string(), z.object({
    min: z.number().int().optional(),
    max: z.number().int().optional(),
    hidden:   z.boolean().optional(),         // hide this field from the merchant

  })).default({}),

  // Tier gating
  requiresFeature: z.array(z.string()).default([]),
  whenMissing: z.enum(["hide","downgrade","upsell"]).default("hide"),
  downgradeTo: z.string().optional(),         // section type to fall back to
});
```

### 4.3 Adding a new template — the decision tree

Your question: *"how can I add or manage different templates, because each variant has some similar or new design?"* Here is the triage, in cost order. **Always try to land in a cheaper row.**

| New design need | Mechanism | Cost | Who does it |
|---|---|---|---|
| Different colours / fonts | New **preset** JSON | **15 min** | designer |
| Same blocks, different order/copy | New **manifest**, existing sections | **30 min** | content author |
| Same content, different arrangement | New **variant** on an existing section (`data-variant` + CSS) | **1–2 h** | front-end dev |
| Different page proportions | New **shell** (§4.4) | **2–3 h** | front-end dev |
| Genuinely new block | New **section type** (folder + schema + meta + fixtures) | **2–4 h** | dev + designer |
| New kind of page | New **page kind** + route | **1–2 days** | dev |

The library is designed so that after the first ~15 templates, **row 2 handles ~80% of requests** — new templates become pure content work at ~30 minutes each. Rows 3–5 shrink as the library fills in.

Governance that keeps it from rotting:

- **No new section type without two intended uses.** One-offs become settings on an existing section.
- **New section types need a design review.** 58 is a healthy library; 120 is an unmaintainable one.
- **Every section lands with all its variants, fixtures and a visual-regression baseline** — not retrofitted later.
- **Reserve manifest IDs** `landing-NN-slug` / `shop-NN-slug` so filenames sort usefully at 75 files.

### 4.5 Where manifests live — git first, DB later

**Phase 1 (now): JSON files in git**, `packages/themes/templates/{landing,shop}/*.json`, loaded into memory at boot.

- 75 manifests × ~4 KB = **~300 KB of RAM.** Irrelevant on a 4 GB box.
- Code review, diffs, blame, rollback via `git revert` — all free.
- Zero DB queries to resolve a template.
- Schema validation runs in CI, so a broken manifest never reaches production.

**Phase 9+ (only if a non-developer must author templates): a `template_versions` table**, with an in-process LRU in front of Valkey in front of Postgres.

```sql
CREATE TABLE template_versions (
  template_id   text    NOT NULL,
  version       integer NOT NULL,
  tier          text    NOT NULL,
  manifest      jsonb   NOT NULL,
  status        text    NOT NULL DEFAULT 'draft',
  published_at  timestamptz,
  created_by    uuid,
  PRIMARY KEY (template_id, version)
);
```

**Do not build this yet.** It adds a cache layer, an authoring UI, a preview pipeline and a publish workflow to buy a convenience nobody needs while your template authors sit next to the repo. The manifest *schema* is identical either way, so the migration is a loader swap — build the git version, keep the option.

### 5.1 How it works

The dashboard never knows about templates. It knows about **schemas** and walks a **tree**.

```

                 └─ for each field in schema.shape

                      ├─ skip if constraints.hidden
                      ├─ skip if showIf evaluates false
```

### 5.2 Control vocabulary — keep it finite

The form renderer is a switch with this many cases and no more. Every new control is permanent surface area, so the list is deliberately short.

| Control | Stores | Notes |
|---|---|---|
| `text` | `string` | maxLength from schema; Bangla-safe input |
| `textarea` | `string` | `rows` hint |
| `richtext` | sanitised HTML | **Server-side allow-list** (`b i em strong u a ul ol li br p`). Never trust the client. |
| `number` | `number` | min/max/step from schema |
| `money` | `bigint` **poisha** | Renders as ৳, stores integer. Invariant #2. |
| `toggle` | `boolean` | |
| `select` | `string` | options from `z.enum` |
| `multiselect` | `string[]` | |
| `color` | `string` | hex; contrast warning against the current preset |
| `image` | `{ mediaId, alt }` | Media picker → **never a raw URL** (§6.1) |
| `video_url` | `string` | YouTube/Facebook/direct, validated by host allow-list |
| `icon` | `string` | **Fixed set only** — arbitrary SVG upload is an XSS vector |
| `link` | `{ kind, value }` | `kind: anchor \| page \| product \| collection \| external \| phone \| whatsapp` |
| `product_ref` | `uuid` | tenant-scoped picker |
| `collection_ref` | `uuid` | tenant-scoped picker |
| `repeater` | `T[]` | min/max; drag-reorder; **the banner mechanism** |
| `group` | `object` | nesting only; no UI of its own |

Seventeen controls cover every editable thing in your requirement — *"change img, banner, logo, txt, offers, colors, etc."*

### 5.3 Constraint resolution order

A field's effective bounds are merged, most specific last:

```
schema .default()/.min()/.max()
  → section meta defaults
  → template instance `constraints`      ← min:3, max:3
  → entitlement limits                   ← e.g. imagesPerProduct, storageMb
  → runtime (e.g. media quota reached)
```

**The resolved bounds must be enforced in all three places:** the form (UX), `PUT /theme` (integrity), and the renderer (defence in depth — a snapshot violating bounds renders safely rather than crashing). A form-only constraint is a suggestion, not a constraint.

### 5.4 Schema delivery to the browser

Build a single JSON artefact from all section schemas at compile time (`z.toJSONSchema()` + the `ui()` metadata), content-hash it, serve it from the CDN with a 1-year immutable cache:

```
/cdn/theme-schemas/a4f91c2e.json      ~60–90 KB gzipped for ~58 sections
```

One cached fetch per dashboard build. If that grows uncomfortable, split by tier (`landing.json` / `shop.json`) and load only what the store's plan can use — a Package 1 merchant never needs shop schemas.

**Do not build an API endpoint that generates schemas per request.** They're identical for every merchant and change only on deploy.

### 5.5 Save / validate / publish

```
POST /api/theme/draft           ← autosave, debounced ~2 s
  requires permission: theme:manage                 (fixes M-20)
  for each section:
    registry[type].settingsSchema
      .superRefine(applyConstraints(instance.constraints))
      .parse(settings)                              (fixes M-19, H-14)
  sanitise every richtext field server-side
  verify every mediaId belongs to this store        ← IDOR guard
  verify every product_ref/collection_ref is tenant-scoped
  → store_themes.draft = tree, bump draft_revision

POST /api/theme/publish
  requires permission: theme:manage
  re-validate the whole tree (never trust the stored draft)
  check entitlements: every section's requiresFeature vs can(store, f)
  resolve a SNAPSHOT: manifest defaults + merchant overrides + preset + tokens
  → store_themes.published = snapshot
  → store_themes.published_version += 1
  → insert store_theme_revisions row                ← rollback
  → purgeStoreCache(storeId, ["theme","home","page:*"])   (invariant #8; fix H-5 first)
```

Two details that matter:

- **Validate again at publish.** The draft was validated at save, but schemas can change between save and publish (a deploy), and the draft row is mutable storage.
- **Autosave the draft, never the published tree.** The live storefront must change only on an explicit publish.

|---|---|

| `handleSave` overwriting 6 named keys | `POST /theme/draft` with the whole tree |

### 5.7 Template switching

Switching templates is destructive in a way merchants won't anticipate — it must be explicit and reversible.

1. Merchant picks a new template in the gallery.
2. Server computes a **content carry-over map**: for each section type present in both trees, in document order, copy compatible settings (`hero_product.ratingScore` survives; `banner_carousel.slides[0].image` survives if the new template also has ≥1 banner slot).
3. Show a **plain-language diff** before committing: *"3 banners → 1 banner (2 images will be unused)", "Video section is new (empty)", "Size guide has no equivalent and will be removed."*
4. On confirm, write the merged tree to **`draft`** only. The live site is untouched until publish.
5. Always snapshot the previous published tree into `store_theme_revisions` so "undo" is one click.

**Never discard uploaded media on a template switch.** Orphaned media stays in the library; §6.3 handles collection.

## 6. Merchant customisation

### 6.1 Media: store IDs, never URLs (**T-2**)

This is the single most consequential storage decision in the design.

```jsonc
// WRONG — what today's untyped `settings` invites
{ "image": "https://cdn.example.com/abc.webp" }

// RIGHT
{ "image": { "mediaId": "0193f2a1-…", "alt": "ঈদ কলেকশন ব্যানার" } }
```

Storing a raw URL costs you four things:

1. **No `srcset`.** The plan's image pipeline produces 3 widths (360/720/1080). A URL string knows about one. Your ≤80 KB above-fold budget depends on serving the right width.
2. **No garbage collection.** You can't know whether an R2 object is still referenced, so storage grows forever against a `storageMb` limit.
3. **A `blob:` bug class returns.** A client-side pipeline that hands the form a `blob:` URL and lets it be persisted produces images that work in the editing session and 404 afterwards.
4. **No integrity.** Nothing stops a merchant pasting another tenant's CDN URL into a settings field.

So you need a generic `media` table (also fixing **M-18**, **H-11**, **H-10**):

```sql
CREATE TABLE media (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  store_id     uuid NOT NULL REFERENCES stores(id) ON DELETE CASCADE,
  kind         text NOT NULL,            -- banner | logo | product | gallery | favicon | og
  r2_key       text NOT NULL,
  widths       jsonb NOT NULL DEFAULT '[]',   -- [{w:360,key:…,bytes:…}, …]
  bytes        integer NOT NULL DEFAULT 0,
  content_type text NOT NULL,
  width        integer, height integer,
  alt_text     text,
  status       text NOT NULL DEFAULT 'pending', -- pending | ready | failed
  checksum     text,
  created_at   timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX media_store_kind_idx ON media(store_id, kind, created_at DESC);
```

`product_images` becomes a join from `products` to `media` (or gains a `media_id`), so one upload path serves products, banners, logos and OG images.

Three rules the audit's findings make mandatory:

- **Presigned PUT must bind `content-type` and `content-length`** (**H-10**), or a merchant uploads a 40 MB TIFF — or an HTML file — to your CDN origin.
- **`/media/verify` must actually insert the row** (**H-11**) and must `HEAD` the object first. Today it inserts nothing, so uploads are invisible to the app.
- **Objects that fail verification must be deleted,** not left to accumulate (**H-10**).

### 6.2 Image pipeline for banners

Master Plan §6 specifies client-side resize to 3 widths, WebP with a Safari JPEG fallback, presigned PUT to R2, then HEAD verification — **no server-side `sharp`**, because a 2 vCPU box cannot afford image processing on the request path. That is the right call and it applies to banners too.

Audit **M-17** notes the resize runs on the main thread. For banners this matters more than for product photos: a merchant uploading 3 banners at 4000×3000 from a mid-range Android will freeze the dashboard for seconds. **Move the resize into a Web Worker** with `OffscreenCanvas` and `createImageBitmap`, and report progress per file.

Per-section `maxBytes` in the schema (`300_000` for a hero banner) should be enforced **after** client resize and **again** server-side via the presign constraint.

### 6.3 Orphaned media

Template switches and section deletions leave media unreferenced. A nightly BullMQ job:

1. Collect every `mediaId` referenced in `store_themes.draft`, `store_themes.published`, every `pages` row (draft + published), **every `store_theme_revisions` snapshot**, and `product_images`.
2. Mark unreferenced `ready` media as `orphaned_at = now()`.
3. Delete R2 objects for media orphaned **> 30 days** and still unreferenced.

The revision-snapshot step is essential: skip it and a rollback restores a page whose images you deleted last night. The 30-day grace handles the merchant who removes a section and puts it back.

### 6.4 Colours, tokens and fonts

The preset system already works. Three additions:

**1. Token overrides** — keep the plan's `tokenOverrides` on top of a preset, so a merchant can match their brand without abandoning a coherent palette:

```ts
// store_themes.token_overrides
{ "primary": "#1E40AF", "radius": "0.5rem" }
```

Resolution: `preset → tokenOverrides → CSS custom properties` inlined by `generateThemeCssVariables()` (which already does exactly this and needs only to accept the override layer).

**2. Contrast guard.** A merchant who picks a pale yellow primary gets unreadable buttons. Compute WCAG contrast in the colour picker and warn (don't block) below 4.5:1 against surface. Cheap to add, prevents a whole class of "my site looks broken" tickets.

**3. Font pairings.** All six presets use `'Hind Siliguri', sans-serif`. Add 2–3 Bangla-capable pairings (e.g. Hind Siliguri, Noto Sans Bengali, Baloo Da 2) as a `fontPairing` token:

```ts
"heading": "'Baloo Da 2', cursive", "body": "'Hind Siliguri', sans-serif"
```

6 presets × 3 pairings = 18 palettes for a day's work. **Self-host the fonts** (subset to Bengali + Latin, `font-display: swap`, preload the body weight) — a third-party Google Fonts request costs an extra DNS + TLS handshake against a 2.0 s LCP budget on Bangladeshi mobile networks.

### 6.5 What the merchant can and cannot change

| Can change | Cannot change |
|---|---|
| All text, in Bangla or English | Section markup / DOM |
| All images, via the media library | Which section types exist |
| Preset + token overrides | CSS (no custom-CSS field — XSS + support nightmare) |
| Section enable/disable (unless `locks.removable: false`) | Locked sections |
| Section order (unless `locks.movable: false`) | Fields with `constraints.hidden` |
| Variant (unless `variantLocked`) | Anything beyond `allowedPresets` |
| Repeater items **within min/max** | Exceeding template or plan limits |
| Offers, prices, countdown targets | Section schemas |

**No custom-CSS field.** It looks like a cheap win and becomes a permanent stored-XSS surface, an unanswerable support queue, and a guarantee that every future design change breaks someone's store.

## 7. One landing library for Packages 1 and 2

Your words: *"that same 40-50 landing page will be shown to user of Package 2 but with multiple landing page variations."*

The manifest already declares `pages` and per-page `variants`. The difference is entirely in **entitlements + routing**.

### 7.1 Package 1 — one page

```
limit(store, 'pages') = 1
can(store, 'landing') = true
can(store, 'template_variants') = false
```

- Exactly one `pages` row, `kind = 'landing'`, slug `''`, served at the store root.


- Up to 10 `pages` rows. Each one independently chooses a manifest, a variant, a preset (within `allowedPresets`) and its own content.

- **Variants enable A/B testing from one manifest.** `fashion-boutique-03` has `default`, `short` and `video-lead`. A merchant runs two pages from the same template with different variants and compares conversion.
- Per-page pixel/CAPI config so campaigns attribute correctly.

### 7.3 The schema that supports it

```sql
CREATE TABLE pages (
  id                 uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  store_id           uuid NOT NULL REFERENCES stores(id) ON DELETE CASCADE,
  slug               text NOT NULL,              -- '' = root
  kind               text NOT NULL,              -- landing | home | product | collection | custom
  title              text NOT NULL,
  template_id        text NOT NULL,
  template_version   integer NOT NULL,

```

Note the partial unique index — exactly one primary page per store, enforced by the database rather than by application code that will eventually race.


**Never compare plan names** (invariant #6). `store.plan === 'package_2'` scattered through the codebase is what makes pricing changes a migration project.

## 8. One shop library for Packages 3 and 4

Your words: *"that same template will be used for package 4 with more feature."*

**The difference between Packages 3 and 4 is features, not design.** Forking the manifests would double the authoring work and guarantee drift. Instead, sections declare what they need and the resolver decides.

### 8.1 Three resolution modes

```jsonc
{ "id": "grid", "type": "product_grid_pro",
  "requiresFeature": ["shop_pro"],
  "whenMissing": "downgrade",
  "downgradeTo": "product_grid",
  "settings": { "columns": 4, "showWishlist": true, "showQuickView": true } }
```

| Mode | Live page | Editor |
|---|---|---|
| `hide` (default) | section omitted entirely | section hidden |
| `downgrade` | renders `downgradeTo` with the overlapping settings | shows the basic section + "More options on Package 4" |
| `upsell` | **omitted** | greyed card + upgrade CTA |

`upsell` must never render on the live storefront — only in the editor. A greyed upgrade prompt leaking onto a customer-facing page is an embarrassing bug.

### 8.2 Downgrade pairs worth authoring

| Pro section | Falls back to | Lost on Package 3 |
|---|---|---|
| `product_grid_pro` | `product_grid` | wishlist, quick-view |
| `mega_menu` | `header` nav | multi-column categories |
| `filters_sidebar` | `breadcrumb` | faceted filtering |
| `recently_viewed` | — (`hide`) | personalisation |
| `review_carousel` | `trust_badges` | UGC reviews |
| `bundle_offer` | `quantity_discount` | cross-sell bundles |

A downgrade pair is only worth building when the pro section is a **superset**. If the two sections differ structurally, use `hide` — a half-rendered downgrade looks worse than an absent section.

### 8.3 Shop templates declare multiple page kinds

```jsonc
{
  "id": "shop-modern-02", "version": 1, "tier": "shop",
  "shell": "shop-grid",
  "requiresFeature": ["shop"],          // see T-1 — must be satisfiable by P3 AND P4
  "pages": {
    "home":       { "kind": "home",       "title": "Home",       "sections": [ /* … */ ] },
    "collection": { "kind": "collection", "title": "Collection", "shell": "shop-sidebar", "sections": [ /* … */ ] },
    "product":    { "kind": "product",    "title": "Product",    "sections": [ /* … */ ] },
    "cart":       { "kind": "cart",       "title": "Cart",       "sections": [ /* … */ ] }
  }
}
```

`collection` and `product` are **page templates**, not pages — one definition renders every collection and every product. That is why `pages` must be a keyed record rather than an array.

### 8.4 Fixing **T-1** — cumulative features

The current flat sets make `requiresFeature` unusable. Two options; the second is better.

**Option A — spell out every feature on every plan.** Works, but every new feature means editing four lists, and the lists will drift.

**Option B — declare inheritance, resolve at load.** Recommended:

```ts
const PLAN_CHAIN: Record<string, string | null> = {
  pilot:     null,
  package_1: null,
  package_2: "package_1",
  package_3: "package_2",
  package_4: "package_3",
};

const PLAN_FEATURE_DELTAS: Record<string, string[]> = {
  package_1: ["landing", "guest_cod", "incomplete_orders", "pixel", "courier:steadfast",
              "template_library:landing"],
  package_2: ["multi_landing", "custom_domain", "coupons", "template_variants"],
  package_3: ["shop", "customer_accounts", "courier:pathao", "fraud_rules",
              "template_library:shop", "reviews:ugc"],
  package_4: ["shop_pro", "all_couriers", "advanced_reports", "meta_capi"],
};

export function resolveFeatures(plan: string): string[] {
  const out = new Set<string>();
  for (let p: string | null = plan; p; p = PLAN_CHAIN[p] ?? null) {
    for (const f of PLAN_FEATURE_DELTAS[p] ?? []) out.add(f);
  }
  return [...out];
}
```

Package 4 now resolves to `shop_pro` **and** `shop`, `landing`, `multi_landing`, `incomplete_orders`, `pixel`. Section gating works, and so does the rest of the product — Package 4 regaining abandoned-cart recovery and pixel tracking is a bug fix that happens to fall out of this.

Resolve once at load and keep storing the flat array in `plans.entitlements`, so `can()` stays an array lookup and nothing downstream changes. Add a CI assertion that each plan's resolved features are a superset of the plan below it.

Also add template limits:

```ts
limits: {
  pages: 1 | 10 | 20 | 50,          // supersedes landingPages; keep an alias during migration
  templateSwitchesPerMonth: 5 | 20 | 20 | 100,   // optional abuse guard
}
```

### 8.5 Catalogue filtering

```ts
export async function listTemplatesForStore(store: Store) {
  const all = await loadManifests();
  return all.filter(t => {
    if (t.status !== "published") return false;
    if (t.tier === "landing" && !can(store, "template_library:landing")) return false;
    if (t.tier === "shop"    && !can(store, "template_library:shop"))    return false;
    return t.requiresFeature.every(f => can(store, f));
  });
}
```

Packages 1 and 2 see the 50 landing templates. Packages 3 and 4 see the 25 shop templates — and, since features are cumulative after **T-1**, also the landing templates, which is correct: a shop wants campaign landing pages too.

## 10. The demo gallery

Your requirement: *"all these templates will be on home page as demo to customers, need to find an efficient way to show them without consuming a lot of resources."*

Constraint: 2 vCPU / 4 GB. Rendering 75 live previews per visitor is out of the question. The answer is to make the common case cost **zero origin work**.

### 10.1 Tier 1 — static screenshot grid (the home-page gallery)

Generated in CI, never at runtime:

```
.github/workflows/template-gallery.yml
  on: push to main, when packages/themes/templates/** changes
  1. build storefront
  2. boot it against a seeded demo store
  3. for each changed template:
       playwright → demo.yourbrandshop.com/t/{id}?preset={defaultPreset}
       viewport 390×844 (mobile first — your traffic is ~95% mobile)
       screenshot full page → sharp → WebP 400w + 800w
  4. upload to R2 at /t/{id}/v{version}/thumb-{400,800}.webp
  5. commit the manifest `gallery` block back if paths changed
```

Budget:

| Item | Size |
|---|---|
| 1 thumb @ 400w WebP q75 | ~25 KB |
| 1 thumb @ 800w WebP q75 | ~70 KB |
| 75 templates, both widths | **~7 MB total on R2** |
| Gallery HTML (75 cards) | ~15 KB gzipped |
| Above-fold payload (6 eager thumbs) | ~150 KB |
| **Origin CPU per visitor** | **0** |

The gallery page itself:

```astro
<ul class="gc-gallery">
  {templates.map((t, i) => (
    <li>
      <a href={`/templates/${t.id}`}>
        <img
          src={`${CDN}${t.gallery.thumb}`}
          srcset={`${CDN}${t.gallery.thumb} 400w, ${CDN}${t.gallery.thumb2x} 800w`}
          sizes="(max-width: 640px) 45vw, 300px"
          width="400" height="711"
          loading={i < 6 ? "eager" : "lazy"}
          decoding={i < 6 ? "sync" : "async"}
          fetchpriority={i < 2 ? "high" : "auto"}
          alt={t.banglaName}
          style={`background:${t.gallery.accent}`}
        />
      </a>
      <h3>{t.banglaName}</h3>

      </ul>
    </li>
  ))}
</ul>
```

Two decisions carry the efficiency:

- **Presets are CSS swatch dots, not screenshots.** 75 templates × 6 presets would be 450 screenshots (~45 MB) and a CI job that takes 20 minutes. Six coloured dots communicate the same thing for zero bytes.
- **Explicit `width`/`height` + a solid `background`.** No layout shift, and the grid is legible before any image decodes — which matters on a 3G connection.

The gallery page is **fully static**, `s-maxage=86400`, `Cache-Tag: gallery`, purged only when a template is published or deprecated.

### 10.2 Tier 2 — live interactive demo

One route, one shared store, long cache:

```
https://demo.yourbrandshop.com/t/{templateId}?preset={presetId}
```

```ts
// apps/storefront/src/pages/t/[templateId].astro
const { templateId } = Astro.params;
const presetParam = Astro.url.searchParams.get("preset");

const manifest = getManifest(templateId);
if (!manifest || manifest.status !== "published") return new Response(null, { status: 404 });

// HARD RULE: validate preset against the known list, 404 otherwise
const allowed = manifest.allowedPresets ?? Object.keys(DESIGN_PRESETS);
const presetId = presetParam ?? manifest.defaultPreset;
if (!allowed.includes(presetId)) return new Response(null, { status: 404 });

const demoStore = DEMO_STORE;   // one shared, read-only fixture store
const resolved  = resolveTheme({ manifest, presetId, store: demoStore, page: "main" });

Astro.response.headers.set("Cache-Control", "public, max-age=0, s-maxage=31536000");
Astro.response.headers.set("Cache-Tag", `demo,demo:tpl:${templateId},demo:v:${manifest.version}`);
Astro.response.headers.set("X-Robots-Tag", "noindex");
```

**The cache-key rule is the whole design.** `preset` is the only query parameter in the key, it's validated against a known list, and anything else 404s. Without that rule, one `?utm_source=fb&fbclid=…` campaign link turns 450 cacheable URLs into unbounded cache entries and pushes every request to your 2 vCPU origin. Configure Cloudflare Cache Rules to **ignore all query strings except `preset`**.

Other requirements:

- **Separate hostname.** `demo.yourbrandshop.com`, never `{store}.yourbrandshop.com`. Your tenancy is Host-based (invariant #4), and audit **H-9** found the storefront resolving tenants from the *URL path* and fabricating a demo store (`00000000-0000-0000-0000-000000000001`) cached for 24 hours. That hack must be deleted, not extended — a path-based tenant resolver on the live host is a tenant-confusion bug waiting to happen.
- **`X-Robots-Tag: noindex`** on every demo page. 450 near-duplicate pages indexed against your real storefronts is an SEO own-goal.
- **Pre-warm in CI.** After each release, crawl all 75 × 6 = 450 URLs. At 4 concurrent requests that's ~2–4 minutes and leaves the edge fully warm, so the first real visitor never hits the origin.
- **Demo store is read-only.** The checkout section renders but submits nothing — a disabled button with "ডেমো মোড". A live demo that writes orders is a spam vector and pollutes your metrics.
- **Purge only on version bump:** `Cache-Tag: demo:v:{version}` means publishing v3 of one template purges exactly that template's entries.

Steady-state origin cost: **effectively zero.** Cold-cache cost: one SSR render per (template, preset), ~15–30 ms each.

### 10.3 Tier 3 — merchant draft preview

As in Master Plan §5.5: a short-lived signed token, rendered in an iframe inside the editor.

```
GET /preview?token={jwt}      # exp 15 min, claims: storeId, pageId, revision
X-Robots-Tag: noindex
Cache-Control: private, no-store
```

Live updates via `postMessage` from the editor rather than a page reload per keystroke: the editor sends the changed subtree, the iframe re-renders that section client-side for the common controls (text, colour, toggle) and does a full reload only when structure changes (add/remove/reorder section). This keeps editing responsive without hammering the origin.

Never cache preview responses. Never render preview content on the public demo host.

### 10.4 CI budget gates

Performance budgets only hold if a machine checks them. Add to CI:

```
assert manifest validates against templateManifestSchema
assert every section.type exists in SECTION_REGISTRY
assert every section.variant is declared in that section's meta.variants
assert settings parse against the section schema + instance constraints
assert fixtures parse against the section schema
assert sum(jsBytesEstimate)  for default page ≤ 30 KB gz
assert sum(cssBytesEstimate) for default page ≤ 15 KB
assert rendered HTML ≤ 30 KB gz
assert above-fold images ≤ 80 KB
assert each plan's resolved features ⊇ the plan below it        (T-1 guard)
assert Playwright visual snapshot matches baseline, per section × preset
assert Lighthouse mobile LCP ≤ 2.0 s on 3 sampled templates
```

The visual-regression matrix is what makes a 58-section library safe to change. Touching shared button CSS with 75 templates in production and no baselines is how you ship a subtly broken storefront to every merchant at once.

## 11. What to do with the 52 scraped sites

They are `wget` mirrors of WordPress + WooCommerce + Elementor storefronts (§1.12). **Do not import them.** Mine them.

### 11.1 A structured extraction pass (worth ~2 days)

Build a one-off script — `scripts/analyze-reference-sites.ts`, never shipped — that for each mirror records:

1. **Section inventory.** Which of your 58 section types appear, in what order? Output a frequency table. If 40 of 52 sites open with a banner carousel and close with a sticky order bar, that tells you which sections to build in Phase A and what ordering reads as "normal" to a Bangladeshi shopper.
2. **Bangla copy corpus.** Every heading, CTA label, badge and trust line. This is the highest-value extract: your default copy should sound like the market, and *"অর্ডার করতে ফর্ম পূরণ করুন"* vs *"এখনই কিনুন"* is a conversion decision, not a translation one. Copy **conventions**, not sentences.
3. **Offer-badge patterns.** How discounts, free delivery and urgency are expressed — ৳ placement, Bangla vs Latin digits, percentage framing.
4. **Colour and typography census.** Dominant palettes and font choices. Validates (or corrects) your 6 presets against what this market actually uses.
5. **Trust-signal inventory.** Which badges, guarantees and payment logos appear, and where in the page.
6. **Page-length distribution.** Section count per page, so your templates match local expectations rather than Western SaaS norms.

### 11.2 Output

- `docs/research/SECTION_FREQUENCY.md` — ranked section list → drives §12's build order
- `docs/research/BANGLA_COPY_PATTERNS.md` — the copy corpus → drives manifest defaults
- `docs/research/MARKET_DESIGN_NORMS.md` — colour/type/length findings → drives presets and shells

### 11.3 The line not to cross

Mine **patterns**; author **originals**. Do not copy markup, CSS, images, logos or verbatim copy from a competitor's site. The patterns (banner-then-hero-then-USP-then-checkout) are industry convention and free to use. The specific expression is theirs.

Keep the mirrors out of the repository — they're hundreds of megabytes of WordPress output, and committing a competitor's site into your git history is a liability you can't delete. Reference them from `E:\Zatiq easy clone\templets` locally and commit only your derived analysis documents.

## 12. Implementation plan

### 12.1 The sequencing question, stated plainly

The 4 Oct audit's verdict is *"the project is NOT going as planned"* and *"the project is not clear to go live"*, with C1–C8 outstanding: committed super-admin credentials (`admin@gocommerce.bd` / `admin12345`) in git history, a second in-memory session issuer live in production, production running on committed default secrets, no RLS, no oversell protection (zero `FOR UPDATE` in the repo), attacker-knowable Turnstile bypass literals, and no rate limiting anywhere. §9 of the audit notes *"features are being added ahead of the plan's own gate."*

The Master Plan's own rule is **no new features until Phases 0–2 are complete.**

A template engine is a large new feature. Building it now while C1–C8 stand would repeat exactly the pattern the audit called out. But the work splits cleanly:

- **Content work can start today.** Section inventory, Bangla copy research, design of 50 landing layouts, preset and font pairings, the reference-site analysis — none of it touches the running system, and it's the long-lead item (§12.3).
- **Engine work belongs behind the gate.** Schema-driven forms, `store_themes`, media, the demo host — all of it writes to the database and serves public traffic.

So: **do Phase 0 (security) and the design work in parallel; start Phase A engineering when C1–C8 are closed.** That ordering costs you nothing in calendar time, because template authoring is the bottleneck anyway.

### 12.2 Phases

**Phase 0 — prerequisites (blocking, security)**
Close C1–C8. Then the three template-specific blockers:
- **T-1** cumulative features (§8.4) + the CI superset assertion
- **T-2** `media` table, presign with bound content-type/length, `/media/verify` actually inserting, failed-upload cleanup
- **T-3** real Zod validation on theme writes + `theme:manage` permission
Plus: **fix the dead cache purge (H-5)** — a template system whose purge silently no-ops ships stale storefronts, and reports success while doing it. And **delete the path-based tenant resolver + fabricated demo store (H-9)** before building the demo host on top of it.

**Phase A — engine foundation**
Zod 4 upgrade (§3.6). Section registry + generated `SectionType` (§3.3). `templateManifestSchema` with `pages`, `version`, `tier`, `locks`, `constraints` (§4.1). `store_themes` + `store_theme_revisions` + `pages` tables, with RLS policies from day one (§9). Page shells (§4.4). Migrate the 5 existing archetypes to v1 manifests so nothing changes visually. Delete the hardcoded merge block in `engine.ts` (§1.3).
*Exit criterion: the 5 current templates render identically through the new pipeline.*

**Phase B — derived settings forms**
Section schemas + `ui()` hints for the existing 11 sections. Build-time schema artefact on the CDN (§5.4). `Field.tsx` with the 17 controls (§5.2). `ThemeEditor` replacing `ThemeView.tsx` (§5.6). Draft/publish/rollback. Media picker storing `mediaId`. Web Worker image resize (**M-17**).
*Exit criterion: a merchant edits all text, images and colours of an existing template and publishes — and the "3 banners → 3 uploads" behaviour works on a test manifest.*

**Phase C — section library build-out**
Build sections in the order the reference analysis ranks them (§11.2). Each one lands with schema + meta + variants + fixtures + visual baseline. Target ~30 landing sections by the end of this phase.
*Exit criterion: 10 genuinely distinct landing templates authored and passing budget gates.*

**Phase D — template authoring at scale**
Author 40–50 landing manifests. Add 2–4 presets and 2–3 font pairings. CI screenshot pipeline (§10.1). The static gallery page.
*Exit criterion: 50 templates live in the gallery, all within budget.*

**Phase E — shop tier**
The 14 shop-only sections. `requiresFeature` / `hide` / `downgrade` / `upsell` resolution (§8.1). Page-kind routing for product/collection/cart. 20–30 shop manifests.
*Exit criterion: one manifest renders correctly as both Package 3 and Package 4.*

**Phase F — demo infrastructure**
`demo.` hostname, `/t/{templateId}` route with the validated cache key (§10.2), Cloudflare cache rules ignoring all query strings but `preset`, CI pre-warm crawler, signed-token merchant preview (§10.3).

**Phase G (optional, later) — DB-backed authoring**
`template_versions` table, super-admin authoring UI, LRU + Valkey cache. Only once a non-developer needs to author templates (§4.5).

### 12.3 Authoring throughput — the real constraint

Per template, once the library is mature:

| Task | Time |
|---|---|
| Choose sections, order, variants | 10 min |
| Write Bangla + English default copy | 15 min |
| Source/prepare demo images | 10 min |
| Pick preset, set `allowedPresets`, tags, `bestFor` | 5 min |
| Review on mobile, fix | 10 min |
| CI screenshot (automated) | 0 |
| **Total** | **~50 min** |

- 50 landing templates ≈ **40–45 hours** ≈ 1–1.5 weeks for one person, **parallelisable across authors**.
- 25 shop templates ≈ 25–30 hours.
- Add ~30% for the first 10 while conventions settle.

**The constraint is authoring and QA, not engineering.** Which is precisely the outcome the data-vs-code split is designed to produce — and the reason to start the design work during Phase 0 rather than after it.

## 13. Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Section library bloats past ~80 types | Unmaintainable; CSS budget breached | Two-use rule; design review for new types; variants before new sections (§4.3) |
| Shared CSS grows past 15 KB inlined | LCP budget missed on every store | Per-section ≤1 KB budget; `data-variant` not new components; CI gate (§10.4) |
| Templates all look alike | Merchants churn; 50 templates feel like 5 | Template-declared shells (§4.4); variant diversity; mine market norms (§11) |
| Merchant deletes a required section | Broken checkout, zero orders | `locks.removable: false` on checkout/header/sticky; renderer-side fallback |
| Template edit breaks live stores | Mass visual regression | Published **snapshots**, not pointers; opt-in version upgrade with diff (§5.5) |
| Demo cache blown by query params | Origin overload on 2 vCPU | Cache key = `preset` only, validated, 404 otherwise; Cloudflare rule (§10.2) |
| Orphaned media fills `storageMb` | Merchants hit quota mysteriously | Nightly scan incl. revision snapshots, 30-day grace (§6.3) |
| Stored XSS via rich text | Tenant-wide compromise | Server-side allow-list sanitisation; fixed icon set; **no custom CSS** (§6.5) |
| Cross-tenant media reference | Data leak | Verify every `mediaId` belongs to the store on save; RLS on `media` (§5.5, §9.5) |
| Section schema change breaks old snapshots | Stores fail to render | `schemaVersion` + `migrate(old)→new`, applied lazily at resolve, persisted on next publish |
| **T-1** ships unfixed | Feature gating silently hides sections on Package 4 | Cumulative features + CI superset assertion (§8.4) |
| Engine built before C1–C8 closed | Audit's "features ahead of the gate" repeats | Parallel content work; engine starts at the Phase 0 exit (§12.1) |

## 14. Decision summary

| Question | Answer | Why |
|---|---|---|
| How are 75 templates represented? | JSON manifests in git | Adding one = content work, not a deploy |
| Templates as code or data? | **Data.** Sections are code. | 58 components × combination ≫ 75 forks |
| Where does variety come from? | sections × order × variant × preset × shell | 450 looks from ~58 components |
| How do variants work? | `data-variant` CSS switches, same DOM | 15 KB inlined-CSS budget |
| How does P1 differ from P2? | Page count + variants, same manifests | No duplication; upgrade is a limit change |
| How does P3 differ from P4? | `requiresFeature` + hide/downgrade/upsell | Same manifests; difference is features |
| How does "3 banners" work? | `repeater` + instance `constraints.min=max=3` | Form derived from the resolved tree |
| Who writes the settings form? | Nobody — it's derived from schemas | Template #51 needs zero dashboard changes |
| Where do images live? | `media` table; settings store `mediaId` | `srcset`, GC, integrity, no `blob:` bugs |
| How is the gallery served? | Static CI WebP screenshots on the CDN | ~7 MB total, zero origin CPU |
| How are live demos served? | One shared store, separate host, 1-year edge cache, validated cache key | ~0 origin cost after warm-up |
| Can editing a template break live stores? | No — `published` is a resolved snapshot | Upgrades are opt-in, with a diff |
| What about the 52 scraped sites? | Design reference only; never import | 220 KB/page, Elementor soup, IP risk |
| When does this get built? | Design now, engine after C1–C8 + T-1/T-2/T-3 | Authoring is the bottleneck anyway |

## Appendix A — Control vocabulary reference

| Control | Zod type | Storage | UI hints | Validation notes |
|---|---|---|---|---|
| `text` | `z.string()` | `string` | `label`, `placeholder`, `maxLength` | trim; reject control chars |
| `textarea` | `z.string()` | `string` | `rows`, `maxLength` | as above |
| `richtext` | `z.string()` | sanitised HTML | `toolbar` | **server-side allow-list**, not client |
| `number` | `z.number().int()` | `number` | `min`, `max`, `step`, `suffix` | clamp server-side |
| `money` | `z.bigint()` | **poisha** | `currency: "BDT"` | integer only (invariant #2) |
| `toggle` | `z.boolean()` | `boolean` | `label`, `help` | — |
| `select` | `z.enum([…])` | `string` | `options` | must be in enum |
| `multiselect` | `z.array(z.enum)` | `string[]` | `options`, `max` | — |
| `color` | `z.string().regex(hex)` | `string` | `presetSwatches` | WCAG contrast warning |
| `image` | `imageRef()` | `{mediaId, alt}` | `aspect`, `maxBytes`, `recommended` | mediaId must belong to store |
| `video_url` | `z.string().url()` | `string` | `providers` | host allow-list |
| `icon` | `z.enum(ICONS)` | `string` | `set` | **fixed set only**; no SVG upload |
| `link` | `linkRef()` | `{kind, value}` | `kinds` | refs tenant-scoped; external = https only |
| `product_ref` | `z.string().uuid()` | `uuid` | — | must belong to store |
| `collection_ref` | `z.string().uuid()` | `uuid` | — | must belong to store |
| `repeater` | `z.array(z.object)` | `T[]` | `min`, `max`, `itemLabel` | **instance `constraints` override schema bounds** |
| `group` | `z.object({})` | `object` | `collapsible` | structural only |

Conditional display on any control: `showIf: { field, equals }`. Evaluated in the form and ignored by the renderer (a hidden field keeps its stored value).
