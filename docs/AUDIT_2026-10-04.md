# Go Commerce BD — Independent Code Audit vs. Master Plan v2

**Audit date:** 4 Oct 2026
**Auditor:** read-only inspection of `E:\Go Com` @ `9f5bbc2` (branch `main`, clean tree)
**Baseline:** `docs/MASTER_PLAN.md` (Master Plan v2, 1 Oct 2026) — §4 architecture, §5 designs, §6 data model, §7 phases, §10 security checklist, §11 AI invariants
**Method:** every claim below is grounded in a file/line read during this audit. No files were modified.

## 0. Verdict

**The project is NOT going as planned.**

The *Bangladesh-specific product surface* (incomplete-order capture, tele-sales call statuses, advance bKash verification, Steadfast booking + CSV, Facebook catalog feed, poisha money, Bangla phone normalisation, 5-package entitlements, section-based theme engine, client-side 3-width image pipeline) is genuinely built and, in most places, built well. That is the hard-to-copy part and it is real.

The *foundation that Master Plan v2 was written to fix* is still largely unfixed, and in two places it has regressed into something more dangerous than the v1 demo:

| Plan claim | Reality |
|---|---|
| Phase 1 exit: "a merchant of store A cannot read store B, proven by test" | **No RLS policies exist anywhere in the repo. No cross-tenant test exists.** |
| Phase 1 exit: "Better Auth is the only session issuer" | **A second, hand-rolled session issuer exists with hardcoded super-admin credentials and an in-memory user store that is active in production.** |
| Phase 2 exit: "no overselling under concurrency" | **No `FOR UPDATE`, no conditional decrement, no rowcount check anywhere.** |
| Phase 0 exit: "secrets in Coolify, never in git" | **The production compose file sets env vars under names the API never reads; the API therefore runs on committed default secrets.** |
| Phase 3 exit: "Turnstile on checkout" | **Turnstile has hardcoded bypass tokens, defaults to Cloudflare's always-pass secret, and no frontend ever renders the widget.** |

Net position against the plan's own gate — *"nothing with real customer data goes on a public URL before Phase 2 exit criteria pass"* — **the project is not clear to go live.** The blocking set is small and concrete (Section 2, C1–C11) and is roughly 2–3 weeks of focused work, not a rewrite.

## 1. What is genuinely done well (keep, don't touch)

These are confirmed correct in code and should be protected from regression:

- **`packages/contracts`** — `convertBanglaToAsciiDigits`, `bdPhoneRegex`, `normalizeBdPhone`, `poishaSchema`, `formatBdt`. The phone schema correctly transforms → refines → re-transforms. This is the cleanest package in the repo.
- **`packages/db/src/crypto.ts`** — AES-256-GCM with a 12-byte IV, auth tag stored separately, `keyVersion` column for rotation; scrypt (N=16384, r=8, p=1) with 16-byte salt and `timingSafeEqual` comparison. Textbook.
- **`packages/db/src/entitlements.ts`** — `can()` / `limit()` with a 5-minute cache, 5 packages, no plan-name comparisons. Exactly invariant #6.
- **`packages/themes`** — 11 section types, design presets, starter templates, `resolveTheme()` with preview overrides, `generateThemeCssVariables()`. H2 is substantially addressed.
- **Atomic order numbering** — the `INSERT … ON CONFLICT DO UPDATE … RETURNING current_value` upsert on `store_counters` (`packages/db/src/tenant.ts:150`) is the correct fix for B4.
- **Per-store encrypted courier credentials** — `store_credentials` + `SteadfastCourierService.createParcel` throwing when per-store keys are absent (`apps/api/src/services/steadfast.ts:33`). B3 fixed properly.
- **Authenticated merchant API** — every route in `admin.ts` carries `requireSession` + `requireStoreMembership` + `requirePermission(...)`. B1 fixed.
- **Tenant resolution for `/v1`** — `middleware/tenant.ts:17-26` explicitly skips Host-based resolution for `/v1`, and the dev fallback is gated behind `NODE_ENV=development && DEV_TENANT_FALLBACK=1`. Correct.
- **Media pipeline client side** — `apps/dashboard/src/lib/image-compress.ts` produces 360/720/1080 WebP with a real Safari JPEG fallback, uploads 3 presigned PUTs in parallel, then calls `/media/verify`. Server does zero decoding; `verifyUploadedObject` enforces a 2 MB cap and an image content-type allow-list.
- **Resource budget** — `deploy/coolify/docker-compose.prod.yml` memory limits (pg 1024M / api 512M / storefront 512M / worker 256M / valkey 256M / cloudflared 128M) match §9, and Valkey correctly runs `--maxmemory-policy noeviction` for BullMQ.
- **Zero inbound ports** — Cloudflare Tunnel only; Postgres and Valkey are not published.

## 2. CRITICAL findings (block go-live)

### C1 — Hardcoded platform super-admin credentials, committed to git

```
apps/api/src/routes/auth.ts        memUsers.set("admin@gocommerce.bd", defaultSuperAdmin)
                                   memUsers.set("superadmin@demo.com", defaultSuperAdmin)
                                   hashPassword("admin12345")        ← at module import, ungated
packages/db/src/create-super-admin.ts   email ?? "admin@gocommerce.bd"; password ?? "admin12345"
packages/db/src/seed.ts                 hashPassword("admin12345"), role: "super_admin", no NODE_ENV guard
```

`admin@gocommerce.bd` / `admin12345` and `merchant@demo.com` / `demo12345` are in the public source tree. `pnpm db:seed` and `pnpm db:create-admin` write them into whatever `DATABASE_URL` points at — including production. The login route additionally accepts the aliases `admin`, `superadmin`, `super_admin` as identifiers mapping to that account.

**Impact:** full platform compromise from a published password. This is the single worst finding.

### C2 — A second, hand-rolled session issuer that is active in production

`apps/api/src/routes/auth.ts` maintains four module-level maps — `memUsers`, `memAccounts`, `memStores`, `memSessions` — populated at import time and consulted on **every** request, with **no `NODE_ENV` guard**:

- `POST /login` tries the DB, swallows all errors (`catch { /* Database offline, fall back to memory */ }`), then falls through to the memory maps (lines ~528–578).
- On success it mints a 32-byte token, inserts a real row into the Better Auth `session` table, **and returns the raw token in the JSON response body**.
- `GET /me` checks `memSessions` **before** the database.
- `extractToken()` accepts `Authorization: Bearer` as well as the cookie.

This directly violates the plan's Phase 1 exit criterion ("Better Auth is the only session issuer"). It also means a transient DB outage silently degrades authentication to an in-memory store seeded with the C1 credentials, and the in-memory maps grow without bound on every registration.

### C3 — Production runs on committed default secrets (env-name mismatch)

| `apps/api/src/config.ts` reads | `docker-compose.prod.yml` sets | Result in production |
|---|---|---|
| `SESSION_SECRET` (default `"dev_secret_must_be_changed_in_prod_12345"`) | `BETTER_AUTH_SECRET` (line 67) | **Session cookies signed with a secret that is in git → forgeable sessions for any user** |
| `ENCRYPTION_MASTER_KEY` (default `"0123…cdef"`) | `ENCRYPTION_KEY_CURRENT` (line 77) | **Courier API keys encrypted with a known key → a DB dump yields plaintext merchant credentials** |
| `R2_ACCOUNT_ID` / `R2_ACCESS_KEY_ID` / `R2_SECRET_ACCESS_KEY` / `R2_BUCKET_NAME` | `CF_ACCOUNT_ID` / `CF_R2_*` (lines 71-74) | All image uploads 403 |
| `CLOUDFLARE_ZONE_ID` / `CLOUDFLARE_API_TOKEN` | `CF_ZONE_ID` / `CF_API_TOKEN` (lines 75-76) | Cache purge silently disabled |
| `TURNSTILE_SECRET_KEY` | *(never set)* | Falls back to the always-pass test secret |
| `FIREBASE_*` | set on `worker` only | API-side FCM inert |

Every secret in `config.ts` uses `.default(...)` rather than being required in production, so the app **fails open** instead of refusing to boot. Not one secret name in the deployment manifest matches the application.

### C4 — Row-Level Security does not exist

Repo-wide greps for `ENABLE ROW LEVEL SECURITY`, `CREATE POLICY`, `app_rw`, `app_ro` return **zero matches**. `withTenant()` dutifully executes `SELECT set_config('app.store_id', …, true)` (`packages/db/src/tenant.ts:54`) — a setting no policy reads. The entire §5.2 defence-in-depth layer is absent, so tenant isolation rests solely on developers remembering `eq(table.storeId, …)` in every query — and §2 C5 shows that has already failed twice.

The storefront container is additionally given the same read-write `DATABASE_URL` as the API (`docker-compose.prod.yml:130`), so an SSRF or template-injection bug in Astro is a full-write database compromise. B5 is unresolved.

### C5 — Queries that omit the tenant predicate (invariant #5)

- `apps/api/src/routes/admin.ts:437` — courier booking updates the order with `.where(eq(orders.id, order.id))` and **no `storeId`**.
- `apps/api/src/routes/incomplete.ts:49` — lead update uses `.where(eq(incompleteOrders.id, existing.id))` and no `storeId`; the whole route runs on the raw `db` handle, **outside `withTenant()`**.

Both are presently reachable only with an id the caller already proved access to, so neither is a live cross-tenant read *today* — but with no RLS behind them (C4) they are one refactor away from being one, and they violate the invariant as written.

### C6 — Overselling is unprotected

`apps/api/src/routes/checkout.ts:130-146` selects variants under a comment that says *"Lock variants"* but contains **no `FOR UPDATE`** (grep: zero occurrences of `FOR UPDATE` in the entire repo). The stock decrement that follows is unconditional — no `WHERE stock_quantity >= :qty`, no affected-rowcount check. Two concurrent orders for the last unit both succeed and stock goes negative. The plan's Phase 2 exit criterion is unmet, and the test that claims to cover it (below) asserts only HTTP 201.

### C7 — Turnstile is decorative

```
apps/api/src/services/turnstile.ts:24   if (token === "test-turnstile-token" || token === "XXXX.DUMMY.TOKEN.XXXX") return true;   ← not env-gated
apps/api/src/services/turnstile.ts:28   process.env.TURNSTILE_SECRET_KEY || "1x0000000000000000000000000000000AA"            ← Cloudflare always-pass
```

Two attacker-knowable literal strings bypass verification in production, and absent a configured secret every token verifies anyway. Meanwhile grep finds **zero** Turnstile references in `apps/storefront` or `apps/dashboard` — no widget is ever rendered, and `InlineCheckoutForm.tsx` sends no token. So in production, checkout is either rejected for every real shopper (403) or protected by nothing. `/api/incomplete-orders` and `/api/auth/register-store` have no captcha at all.

### C8 — No rate limiting anywhere

Grep for `rate.?limit|rateLimiter` across `apps/` and `packages/`: **zero matches**. `POST /api/auth/login` (which is also reachable on every shopper domain, see C9) has no throttle, no lockout, and no captcha; `POST /api/orders`, `POST /api/incomplete-orders` and `POST /api/auth/register-store` are equally open. On a 2 vCPU box, one scripted client can exhaust Postgres connections, and credential stuffing against C1 is unimpeded.

### C9 — The storefront API proxy is broken *and* over-exposed

`apps/storefront/src/pages/api/[...path].ts`:

```ts
const targetPort = process.env.API_PORT || "3000";
const targetUrl = new URL(url.pathname + url.search, `http://localhost:${targetPort}`);
forwardHeaders.set("Host", `localhost:${targetPort}`);        // line 10
responseHeaders.set("Access-Control-Allow-Credentials", "true"); // line 25
```

Three distinct defects:

1. **Broken in production.** The API lives in a sibling container (`api:3000`). `localhost:3000` inside the storefront container is nothing, and there is no env var for the host — only the port. Every storefront checkout returns 502.
2. **Destroys tenant resolution.** Even with the host fixed, overwriting `Host` means the API's Host-based tenant lookup resolves nothing (the dev fallback is correctly gated), so checkout cannot identify the store. Invariant #4 is broken end-to-end at the integration seam.
3. **Over-exposed.** The catch-all forwards *every* path, so `/api/admin/*`, `/api/auth/login` and `/api/auth/register-store` are reachable on **every shopper domain**, with all request headers (including `Cookie`) forwarded and all response headers (including `Set-Cookie`) returned — on cacheable shopper hostnames, which the plan explicitly forbids (invariant #8).

### C10 — No `.dockerignore`; all three images embed the build context

`.dockerignore` does not exist, and `Dockerfile.api`, `Dockerfile.worker`, `Dockerfile.storefront` all begin the builder stage with `COPY . .`. That copies `.git` (full history), `node_modules`, `ppTemp/`, and **any local `.env`** into image layers that then ship to the registry. It also makes the build context enormous on a 2 vCPU VPS. The runner stages additionally copy the whole dev `node_modules` and run as **root** (no `USER node`).

### C11 — The production stack cannot bootstrap a database

`deploy/coolify/docker-compose.prod.yml` has no migration step — no init container, no `pnpm db:migrate`, no entrypoint hook. A fresh deploy starts an API against an empty schema. Compounding this, `packages/db/migrations/0003_orange_mysterio.sql` (which creates `device_tokens` plus its FKs and three indexes) is **present on disk but absent from `_journal.json` and has no snapshot**, so even a manual `drizzle-kit migrate` skips it, and the next `drizzle-kit generate` will re-emit the same objects as a duplicate migration.

## 3. HIGH findings

**H-1 — Store registration is non-transactional and lies about success.**
`apps/api/src/routes/auth.ts:303-360` performs seven independent `db.insert()` calls (`user`, `account`, `organization`, `member`, `stores`, `session`, `auditLogs`) with no surrounding transaction, wrapped in a `try` whose `catch` only logs (lines 359-363). A failure between inserts leaves orphaned rows — e.g. a `user` with no `account` can never log in — and **any** DB failure still returns HTTP 201 with a session cookie, so the merchant believes their store exists when nothing persisted.

**H-2 — Courier booking has no idempotency and no already-booked guard.**
`POST /courier/book` (`admin.ts`) has no `Idempotency-Key` handling and does not check whether the order already carries a consignment. A double-click creates two Steadfast consignments for one order — a real-money error. It also jumps the order straight to `shipped`, and writes `courierRemittances` with a **hardcoded** `courierDeliveryCharge: 12000` and a 1 % `codServiceFee`, so every merchant's reconciliation is wrong unless their contract happens to match.

**H-3 — The outbox is written but never relayed; the courier queue is never consumed.**
Order creation correctly writes an `outbox` row inside the transaction, but there is no relay: grep finds no `WHERE processed_at IS NULL … FOR UPDATE SKIP LOCKED` loop anywhere. `apps/api/src/worker.ts` consumes only the `gocom-outbox` BullMQ queue, which is enqueued inline from the request path — so if Valkey is briefly down, the event is durably in Postgres and **never delivered**. `courierQueue` (`services/queue.ts:21`) is declared and never consumed by any worker. H5 is unresolved; `INCOMPLETE_CAPTURED` and Meta CAPI remain `console.log` stubs.

**H-4 — Push notifications are inert, and silently report success.**
Two independent breaks:
- `apps/api/src/services/fcm.ts:145-154` — when `FIREBASE_PROJECT_ID`/credentials are absent, `sendOrderNotification` logs *"(Mocked) Sent …"* and returns `{ success: true, mocked: true }`. Ungated by `NODE_ENV`.
- `android/.../GoComFirebaseMessagingService.kt:104` posts the device token to `/api/admin/devices/register` with a bare `HttpURLConnection` and **no credentials**, while `apps/api/src/routes/devices.ts:24` requires a session plus `orders:view`. Registration always 401s, so `device_tokens` stays empty — and (per C11) the table may not even exist.

The "Cha-Ching" order alert — the headline merchant feature — cannot work in production, and nothing in the logs says so.

**H-5 — Cache purge is dead and reports success.**
`services/cloudflare-cache.ts:46-59` returns `{ success: true, status: "skipped_no_creds" }` when the Cloudflare credentials are missing, which per C3 they always are. Storefront pages are served `s-maxage=86400`, so a merchant's price or stock change is invisible to shoppers for 24 hours while the dashboard reports the save succeeded. Also `cachePurgeHistory` is an unbounded module-level array in a 512 MB container.

**H-6 — Idempotency has a race, and a memory fallback that is always on.**
`checkout.ts` reads the idempotency record *before* opening the transaction, so two concurrent requests with the same key both miss and both create orders. `packages/db/src/tenant.ts:197` writes every record into an unbounded module-level `memoryIdempotencyStore` unconditionally, and `:171-183` reads it whenever the DB lookup throws — so in a multi-process deployment idempotency silently becomes per-process.

**H-7 — Order numbers can collide.**
`packages/db/src/tenant.ts:160-167` wraps the correct atomic counter in a `try` whose `catch` falls back to `MAX(order_number) + 1` on **any** error — reintroducing exactly the B4 race the counter was built to remove.

**H-8 — Suspended and soft-deleted stores keep serving.**
`middleware/tenant.ts:51-70` resolves a store by subdomain or custom domain with **no `isActive` / `deletedAt` / `status` filter**, then caches it for 60 s. A suspended (non-paying) or soft-deleted store continues to take COD orders. §5.8's enforcement point is missing.

**H-9 — Storefront resolves the tenant from the URL path, and fabricates stores.**
`apps/storefront/src/pages/[store]/index.astro` derives the store from the path segment, not the Host — a direct invariant #4 violation that also means any store's storefront can be rendered under any hostname. Both page families fall back to a fabricated demo store (`id: "00000000-0000-0000-0000-000000000001"`) when the DB is unreachable, and that fake page is returned with `s-maxage=86400` — so one DB blip poisons the edge cache with a fake storefront for 24 hours. The `host.includes("localhost")` branch is not environment-gated.

**H-10 — R2 presigned PUTs don't constrain content type or size.**
`services/r2.ts:76` signs `X-Amz-SignedHeaders: host` only. The `contentType` argument is never part of the signature, so a holder of the URL can upload **any** content type — including `text/html` — to the public media domain, and there is no `content-length` constraint. `verifyUploadedObject` rejects non-images afterwards, but the object is already stored, publicly addressable, and is **never deleted** on failed verification.

**H-11 — `/media/verify` doesn't record anything.**
`admin.ts:821-896` verifies the three objects and writes an audit-log entry, but **never inserts `product_images` rows**. The widths, byte sizes, content types and `status` columns §5.6/§6 call for are not populated, so the catalog has no server-side record of the images the dashboard just uploaded.

**H-12 — Android merchant shell: arbitrary navigation from an exported activity.**
`android/app/src/main/AndroidManifest.xml` sets `android:usesCleartextTraffic="true"`, `android:allowBackup="true"`, and `MainActivity android:exported="true"` with only a LAUNCHER filter (no App Links verification). `MainActivity.kt:141-143` then does:

```kotlin
val targetOrderUrl = intent.getStringExtra("target_url")
webView.loadUrl(targetOrderUrl ?: defaultDashboardUrl)
```

Any installed app can therefore launch the merchant app pointed at an arbitrary URL, inside a WebView that has `javaScriptEnabled`, `allowFileAccess = true`, third-party cookies accepted, a `shouldOverrideUrlLoading` that returns `false` for everything except `tel:`/`wa.me`, and the `GoComNative` JS bridge attached (the bridge's two methods do check `isCallerOriginAllowed()`, which is the one thing done right here). `checkForAppUpdates()` fetches a version document and hands the returned `downloadUrl` straight to `ACTION_VIEW` with **no signature or hash check**, while `apps/api/src/routes/app-version.ts` ships a placeholder `apkSha256` that is the SHA-256 of the empty string. All domains are the placeholder `app.yourbrand.com`.

**H-13 — `/api/incomplete-orders` is an unauthenticated, unthrottled, uncaptcha'd PII sink.**
`routes/incomplete.ts` accepts name, phone, district and address from anonymous callers, outside `withTenant()`, with no captcha (C7), no rate limit (C8), and no per-phone or per-IP cap. It writes no outbox row, so §5.12's abandoned-cart automation has no trigger.

**H-14 — The merchant API is missing most of its CRUD surface.**
`admin.ts` implements product *create* but no update or delete; no categories, no order detail, no reports, no staff invitation, no pages. A merchant can create a product and then never edit it. `PUT /theme` accepts `body.themeConfig` with **no schema validation** and gates on `products:manage` because no `theme:manage` permission exists.

**H-15 — There is no super-admin application.**
`apps/admin` does not exist; `/v1/platform/*` does not exist; `requireSuperAdmin` does not exist; no Cloudflare Access JWT verification exists. `apps/api/src/routes/admin.ts:899` is literally `export const adminRouter = merchantRouter;`. `apps/dashboard/src/views/SuperAdminView.tsx:25` renders a hardcoded `const tenants = [...]` array. §5.14 is a mock-up, and the only real super-admin capability in the system is the C1 password.

**H-16 — `/health` leaks internal error detail.**
`routes/health.ts` returns `err.message` from the failed `SELECT 1` on a public, tunnel-exposed endpoint — Postgres driver errors routinely include host, port, database and user.

## 9. Standing risks worth naming

- **Assume the deployed session secret and encryption master key are compromised.** They are in git with defaults that the production manifest never overrides. Any session minted so far is forgeable, and any courier credential stored so far is decryptable by anyone with the repo and a database dump.
- **The test suite is actively misleading.** It is green because `createMockTx()` returns constants. Treat current coverage as near-zero for anything touching the database until M-1 and M-2 are fixed; the concurrency and idempotency tests in particular prove nothing today.
- **Several failures are silent by design.** FCM, cache purge, credential saving and store registration all return success when their backing service is unavailable. Production will look healthy while the merchant-facing features that justify the product are inert. Every one of these should become a loud failure.
- **Features are being added ahead of the plan's own gate.** The most recent commits add a Settings view and unified marketing themes, while Phase 1 and Phase 2 exit criteria remain unmet — the plan's rule ("no new features until Phases 0–2 are complete") is not being followed.
